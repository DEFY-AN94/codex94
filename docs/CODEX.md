# Codex development setup

Codex94 provides a Codex-only Git preparation script, a local SessionStart
hook, and a repository startup skill for Codex Cloud. They leave Claude Code's
existing `.claude/` hook unchanged. None of these files runs inside the App or
changes an installed App.

## What preparation does

Run from the repository root:

```bash
python3 -I script/codex_prepare.py
```

The script checks `git rev-parse --is-shallow-repository`. If the result is
`false`, it exits without fetching. If it is `true`, it runs
`git fetch --unshallow --quiet origin`, with terminal credential prompts
disabled and a 30-second fetch timeout, then checks the shallow state again.
Existing authentication helpers (including askpass/SSH configuration) are
preserved and may have their own prompts; preparation does not install or
change them. A timed-out Git process and its helper process group are stopped.
It does not change the checkout, remote configuration, or credentials.
The fetch can update remote-tracking refs and fetch tags under the existing Git
configuration; it does not discover branches outside the configured fetch refs.
"Not shallow" does not mean every branch on every remote has been audited.

Missing Git, failed/unknown shallow-state detection, a failed/timed-out fetch,
or a still-shallow result fails preparation. Diagnostics omit raw Git stderr
and remote URLs. Resolve the environment's Git access and rerun the command.
The default strict mode exits nonzero on failure. The local hook uses `--hook`
to report a warning in session context and allow the conversation to continue;
`security_check.sh` still refuses shallow history.

Never pass `--allow-shallow-history` during development or release validation.
That scanner option belongs to `install.sh`'s explicitly limited source-install
scan; it is not a preparation workaround.

## Codex App and CLI local sessions

The repository registers `SessionStart` in [`.codex/hooks.json`](../.codex/hooks.json).
It resolves the Git root so it also works when a session starts in a subdirectory
or a checkout whose path contains spaces. Startup, resume, clear, and compaction
events use the same idempotent check. Git and Python 3 must be on `PATH`.

After checking out this change, open the project in a supported Codex version.
Project-local hooks require a trusted project configuration and review of the
exact hook definition. In Codex CLI, run `/hooks`, review this project's
SessionStart command, and trust it. New or changed definitions need review;
committing the file does not pre-approve hooks on other computers.

The autogenerated `.codex/environments/environment.toml` stays unchanged.
Its setup script is for new local worktrees, not a universal cloud/session hook.
The project `AGENTS.md` also directs Codex to run strict preparation at task
startup and before relying on historical security scans.

## Current Codex Cloud (App and web)

Do not rely on a repository shell hook being executed by cloud orchestration.
The current cloud environment has **Install script** and **Start skill** fields,
and repository skills are available to cloud tasks. The supplied startup skill
is [`.agents/skills/codex-project-start/SKILL.md`](../.agents/skills/codex-project-start/SKILL.md).

When creating or editing this project's cloud environment:

1. Include the Codex94 repository at a revision containing these files.
2. Ask the setup conversation to use `codex-project-start` as the environment's
   **Start skill**, retaining any unrelated startup requirements. If the editor
   stores instructions rather than a skill reference, direct it to read and
   follow that repository skill.
3. Ensure the **Install script** provides Git, Python 3, ripgrep (`rg`), and
   `jq`. Ask setup to run `python3 -I script/codex_prepare.py` in the Codex94
   checkout and verify the result. A shallow checkout requires access to its
   `origin`; keep that access within the environment's configured network policy.
4. Review and test the prepared environment, then **Publish** or **Republish**.
5. Start a new task and verify preparation ran and
   `git rev-parse --is-shallow-repository` prints `false` before security checks.

Saving or merging repository files does not publish an environment or update
an existing cloud task. New tasks use the published prepared filesystem;
existing tasks retain their own state. Repository refreshes do not necessarily
rerun installation/startup commands, so `AGENTS.md` and the scanner's own guard
remain relevant after checkout changes.

These repository files are ready to select during environment setup; merging
this PR alone does not apply account-wide settings or publish an environment.

## Legacy Codex Cloud

For the separate legacy environment used by some review/integration workflows,
run `python3 -I script/codex_prepare.py` from the Codex94 checkout in both its
**Setup script** and **Maintenance script**. Test a new and a cached session.
The legacy settings are separate from the App's local environment TOML.

## Validation

```bash
python3 -I script/tests/test_codex_prepare.py
python3 -I script/tests/test_security_check.py
python3 -I script/tests/test_release_metadata.py
./script/security_check.sh
git diff --check
```

The preparation tests use disposable local repositories and synthetic Git
failures; they need no GitHub credentials or network access. macOS's
`script/release_check.sh` runs them as part of its gate. Cloud/Linux checks do
not establish Xcode build, hosted App tests, DMG packaging, installer transaction,
or UI smoke results; those remain macOS validation.
